# xsigner — Render + Backblaze B2 + rork-sign

A Render-hosted iOS IPA signing website. The browser uploads directly to a **private Backblaze B2 bucket** using short-lived presigned multipart URLs. Render downloads the inputs into a temporary working directory, signs with the `rorksign` CLI, uploads the result back to B2, and returns a temporary download URL.

## Architecture

- **Render Web Service:** website, API, job queue, `rorksign` executable.
- **Backblaze B2 (S3-compatible API):** private input/output object storage and encrypted job manifests.
- **Multipart uploads:** chunks are uploaded from the browser straight to B2; Render is not the 4 GiB upload proxy.
- **Background worker loop:** signing jobs are queued and polled by the API process, so long signing jobs do not keep a browser HTTP request open.
- **Temporary processing storage:** a Render disk mounted at `/data` holds the input files and signed output only while a job is running.

## Render deployment

The included `render.yaml` defines a new service named **`xsigner`** in Ohio, a Docker build, a `/health` check, a 40 GB work disk, environment variables, and a generated job encryption key. Render's standard web-service deploy flow requires a Git repository containing these files.

1. Push this folder to a new GitHub repository, for example `xsigner`.
2. In Render, create a Blueprint from that repository (or create the Docker web service using the same settings).
3. During initial Blueprint setup, provide the B2 application key ID and application key when prompted. `JOB_ENCRYPTION_KEY` is generated by Render.
4. Deploy the service and wait until the deploy is **Live**. Check `https://xsigner.onrender.com/health` (or the actual Render URL if the service name had to change).
5. Configure the B2 bucket CORS as described below before testing a browser upload.

`render.yaml` uses a persistent disk because signing a multi-gigabyte IPA needs local workspace capacity for downloads, extraction, and repacking. Direct B2 uploads reduce pressure on the Render web request path but do not eliminate local disk/RAM/CPU requirements while rork-sign processes the IPA. The 4 GiB setting is a hard input limit, not a guarantee that every IPA within it will fit: some archives expand substantially, so check the 40 GB disk and Render instance metrics with real test files.

## Backblaze B2 setup

Create or use a **private** B2 bucket named `ipa-xsigner` in the region that matches your endpoint. This starter assumes `us-east-005`:

```text
B2_ENDPOINT=https://s3.us-east-005.backblazeb2.com
B2_REGION=us-east-005
B2_BUCKET=ipa-xsigner
B2_KEY_ID=<your bucket-scoped application key ID>
B2_APPLICATION_KEY=<your bucket-scoped application key>
```

Create a bucket-scoped application key with the minimum required read, write, delete, and list capabilities for that bucket. Do not put credentials in the frontend, source control, issue reports, or screenshots. Do not make the bucket public. If your bucket uses a different region/endpoint, update both the Render environment and CORS configuration.

### Configure bucket CORS

Set the bucket's CORS rules to the contents of [`b2-cors.json`](./b2-cors.json). The rule permits the Render origin to upload parts and read the returned ETag header, while object access still requires a presigned URL. If the actual Render hostname changes, update `AllowedOrigins` to the exact HTTPS hostname. For local development, add `http://localhost:<port>` as an additional origin only while needed.

### Lifecycle safety net

Set a B2 lifecycle rule to abort incomplete multipart uploads after one day. The application itself deletes input IPA/certificate/profile objects after successful signing, deletes them after a signing failure, and deletes completed signed objects/job manifests after 24 hours. The lifecycle rule is an additional safeguard for interrupted processes. If you change the application expiry settings, update your bucket lifecycle policy to match.

## API

- `GET /health` — service/build configuration check.
- `GET /api/config` — public upload-size configuration.
- `POST /api/jobs` — create a job and multipart upload IDs; returns a job token once.
- `POST /api/jobs/:id/part-urls` — mint short-lived multipart URLs for selected parts.
- `POST /api/jobs/:id/complete-upload` — finish and size-verify each multipart object.
- `POST /api/jobs/:id/sign` — queue signing; the password is encrypted in the private B2 job manifest using `JOB_ENCRYPTION_KEY`.
- `GET /api/jobs/:id` — poll job status, using `Authorization: Bearer <jobToken>`.
- `POST /api/jobs/:id/download-url` — request a temporary signed IPA download URL.

All job API endpoints other than creating the job require its bearer token. The browser keeps that token in page memory and does not put it in the download URL. The certificate password is not logged or stored as plaintext; it is cleared from the form after queueing, and the encrypted value is removed from the manifest after signing finishes or fails.

## Security and operational notes

- Keep B2 private and store its credentials only in Render environment variables.
- The `/health` route reports whether B2 settings and the signing executable are present; it does not perform an external B2 read/write probe.
- Public anonymous access to the website can consume signing CPU, so the API has per-IP rate limits. For public launches, add an access gate or per-user quota before advertising the service widely.
- Render disk-backed services are single-instance by design. Keep `MAX_CONCURRENT_JOBS=1` initially; increase only after load testing.
- A job interrupted by a container restart is recovered from the B2 manifest. Do not rotate `JOB_ENCRYPTION_KEY` while queued jobs exist or those jobs cannot decrypt their stored password.
- The P12 password must be passed as a CLI argument because of the current rork-sign command-line interface; the server never logs that argument, and the signing subprocess runs only inside the Render container.
- Always test with an app/profile/certificate you are authorized to use. A successful code-signing operation does not guarantee iOS OTA installation: the device, profile, certificate, bundle identifier and provisioning entitlements must all match.

## Local checks

```bash
npm install
npm run check
npm start
```

The website can start without B2 credentials so the health endpoint works, but creating jobs will return a clear configuration error until the required variables are set.
